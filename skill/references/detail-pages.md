# Detail pages

`detail.mjs` opens each row's own page (the URL in one list column) and adds the fields read there. It is a second pass over a list CSV: collect the list first, with its link column.

## Before writing detail.json

- **Look at several items, not one.** Take 2–3 links far apart in the list, and rows that look different there (another category, no price, a badge), and inspect each: `inspect.mjs <url> --html "<record css>"`, `--probe "<field css>"`. Items of one site often use different layouts (a product with variants, a job without a salary block, an old article on an older template). A selector that works on one sample can miss the field on others.
- **Selectors describe the place, never the sample's content.** Nothing from one item's own text (its name, brand, id, price) goes into a selector: it matches only that item.
- **Set `root` to the main record** (the item itself, not the page). Detail pages usually also show related, similar or recently viewed items with the same classes, sometimes before the record; without `root` a field reads the first match anywhere on the page. With `root`, `expand` clicks only inside it too.
- **Covering two layouts:** a comma list (`"[itemprop=brand], .meta .brand"`) takes the first element in page order that matches any part, not the first part that matches. Check it on a page of each layout, and that its parts cannot both match on one page.
- **Values in attributes:** microdata often sits on `<meta itemprop=… content=…>` with no text: read it with `{ "css": "[itemprop=sku]", "attr": "content" }`.
- **What says the page is there:** put the fields every item has in `require` (only ones you saw on every sample: an optional field there turns the items without it into `empty`). The run waits until they show up (late-rendered pages), and a page without them counts as `empty` instead of becoming a row of blanks. When the content arrives in one block, `waitFor` its container instead. `require` is checked after `setup` and `expand`, so a field behind a click may be in it (the clicks come once another field has shown and stayed for 1 s; if no field shows before the click, each page first waits the full `waitTimeoutMs`). Without `require`, a page is read once every field shows; if one never does, the read waits until nothing changed for 3 s (1 s with `expand`). `require` cuts that wait short on pages that lack an optional field.
- **Data behind a click** ("read more", a collapsed spec table, a tab): `expand` clicks every match inside `root` (the whole page without one) before reading (buttons that show more, not links that leave); `setup` runs fixed steps first (a tab, a language switch). Check with `inspect.mjs <url> --click "<css>" --html "<record css>"`.
- **Column names** must differ from the list's columns (the run refuses otherwise): name them for what they are (`detail_title`, `seller_rating`).
- **A second pass** over a detail output (for pages its rows link to) works the same way; its status column is `detail_status_2`.

## Preview, then run

`--max-rows 5` reads the first 5 links only; the rest are `pending`. Read the summary:

- `fillRate` per column on ok pages. A column far below the others: those items lack the field (a job with no salary, a product with no discount), or show it in another place. Before deciding which, look for the value in the record text the warning quotes from a page where the column is empty; if that text is cut off or the value is not in it, inspect that whole record (`--html "<root>"`), not only the block where the field usually is: if the value is there, widen the selector (a comma list); if not, keep the selector and report the fill rate. Never widen until something matches: that turns a true blank into a wrong value. A column empty everywhere: wrong selector, or it needs a click.
- The preview reads only the first links; a layout that appears later in the list does not show up in it. After the full run, read `fillRate` and `warnings` again and handle new ones the same way.
- `status`: many `empty` pages (the warning gives the reason and examples) means another layout, content that renders late, or a soft block.
- `deadLinks`: links that answered 404 / 410. They count as `empty`; report them, don't retry. Expired items often answer 200 instead (a "no longer available" page, or a redirect to a search page): `root` and `require` make those `empty` rather than a row of the wrong values; report them with the dead links.

Then run with the real `--out`. The same `--out` continues where a run stopped; a preview written to another file is not reused.

## Resuming, retries, blocks

- Every page is written to `<out>.detail.jsonl` when it finishes, and the CSV is rewritten as the run goes. A run that is killed loses at most the page in flight (with `--browser chrome`, the batch in flight: up to 8 pages). Ctrl-C, SIGTERM and SIGHUP stop it cleanly (`stopReason: "interrupted"`). Rerunning the same command skips `ok` and `empty` pages, retries `failed` ones while they have tries left (`maxAttempts`, counted over all runs) and `blocked` ones every time. A changed `fields` / `root` / `require` / `waitFor` / `setup` / `expand` / `expandPasses` / `children` reads every page again; pacing and retry settings do not.
- **Empty pages read again:** an empty page counts as done only once an ok page came after it (or the run ended normally); a run stopped in the middle of a run of empty pages reads them again next time, after the other links. To read every `empty` page again (e.g. after raising `waitTimeoutMs` for slow pages), add `--retry-empty` (with `children`, it also reads again the `ok` pages that had no child row); pages recorded as empty by the bundled browser are read again on their own with `--browser chrome`, and the other way round. Dead links (404 / 410) are never read again.
- `failed` is a page that did not load or answered a server error: usually temporary. Rerun later, or raise `maxAttempts`.
- **Blocked midway.** Sites often serve the first pages and then a captcha, an "access denied" page or a login wall. Three blocked pages in a row stop the run (`stopReason: "blocked"`). Some sites send empty pages instead: after three empty pages with no ok page between them (failed and blocked pages and dead links don't count), the run reads a page that was fine before (a server error on that check is tried once more); if that one is empty or blocked too, it stops the same way and marks those pages blocked, so a rerun fetches them again. Keep what you have, tell the user how far it got, and ask before rerunning the same command with `--browser chrome` ([browser.md](browser.md)). Do not solve captchas or log in for the user; do not lower `delayMs` or raise `concurrency` to get through faster.
- **Empty from the start** (`stopReason: "no-data"`): three pages read empty and none has read ok yet (in this run or before), so there is nothing to compare with. Inspect one of those URLs: if the fields are there, the selectors or `require` miss (fix detail.json; the changed spec reads them again); if the page shows the data in inspect but not in the run, or shows nothing at all, the site may be serving this browser empty pages — ask the user about `--browser chrome`.
- A captcha widget alone (many sites show a small badge in a corner of every page) does not make a page blocked when its fields read; block or login wording on a page that read nothing does.
- Pacing: one page at a time, with a pause of `delayMs`..2×`delayMs` (default 1500 ms) before each. `concurrency` (up to 3) runs pages in parallel in the bundled browser only; use it for sites that clearly tolerate it.

## Child lists

When each item's page holds a list of its own that the user wants (the reviews of each product, the comments under each article, the openings of each company, or every row of a spec table whose keys vary by item). Spec values the user names (weight, size, material) are detail `fields` on the item's row, not children, add `children` to detail.json:

```json
"children": {
  "rows": "[itemprop=review]",
  "fields": { "reviewer": "[itemprop=author]", "rating": { "css": "[itemprop=ratingValue]", "attr": "content" }, "posted": { "css": "time", "attr": "datetime" }, "review_text": "[itemprop=reviewBody]" },
  "require": ["review_text"],
  "max": 200
}
```

- `rows` is CSS for one child row, matched inside `root`. With `children`, `root` must hold both the item's fields and its child list, with the list's load-more controls (`expand` clicks only inside `root`). The list often sits outside the item's own block (comments after the `<article>`, a reviews section after the product section): then set `root` to the nearest container that holds both, often `main`. A wider `root` also widens where the item's own `fields` and `expand` look, and related, similar or recently viewed items inside it (sometimes before the record) reuse the record's classes and child rows (a featured comment under each related article): anchor each item field to the record (`article h1`, `.product-main .price`, not a bare `.price`), anchor `rows` to the item's own list section (`#reviews .review`, `.comments > .comment`), and recheck the fields on 2–3 items. A list rendered inside an `<iframe>` (many embedded comment and review widgets) cannot be read: if inspect shows the rows only inside an iframe, don't tune selectors; leave `children` out and tell the user. Rows the page does not show (a hidden template, the options of a closed `<select>`) are left out: read a dropdown's options as one detail field instead; values that appear only after an option is picked (each variant's price or stock) cannot be read as children. `fields` use the list config's field grammar, relative to the child row; write them from one whole child row (`--html "<rows>"`) and check 2–3 items, one with many children and one with none. `children` takes only `rows`, `fields`, `require` and `max`; `expand`, `setup`, `waitFor` and `root` go at the top level.
- Replies: `rows` also matches rows nested in other rows (a reply inside a comment). Each becomes a child row of its own, in page order. To keep replies apart, add a child field `{ "matches": "<reply container> <rows css>", "replace": [["true", "reply"], ["false", "comment"]] }`; nothing records which comment a reply answers, so say so in the report (and that a "Comments (N)" count may count threads only). For top-level rows only, anchor `rows` to the list: a child combinator (`.comment-list > .comment`) when replies are nested, or `:not(<reply marker>)` when replies are siblings marked by a depth or indent class or attribute; check with `--html` on a page that has replies.
- `fields` still needs at least one field the item's page always shows (its title): it decides whether the page is `ok`, and children are read on `ok` pages only. On a separate reviews page (below), use that page's heading.
- The children are read after `setup` and `expand`: put the button that adds the rest of the list to the rows already shown ("Load more comments", "View all answers") in `expand`, and a step that opens a tab or a section in `setup`. Do not put a pager in `expand`: page numbers or a "Next" button that *replace* the shown rows (the URL stays the same) leave only the last page's rows, because children are read once, after all clicks; read what the first page shows and report that those items have more children than were read. `expand` runs up to `expandPasses` rounds of clicks per page (default 10, 30 with `children`; a load-more is clicked once per round). When no child row is there yet, the run waits up to 3 s for rows that come later than the record, then runs `expand` again. detail.mjs does not scroll: a list that loads only when scrolled into view (many review and comment widgets) never appears by waiting. Put `{ "scrollTo": "<the list's section or placeholder>", "optional": true }` then `{ "waitFor": "<children.rows>", "optional": true, "timeoutMs": 5000 }` in `setup` (optional, because items without children may lack them). `require` drops child rows with that field empty (ads, "write a review" boxes); `max` keeps the first N per page.
- Output: the main CSV gets a `children_count` column (`children_count_2`… when the list already has one): `0` on an ok page without children, blank on a page not read `ok` or whose children could not be read. The child rows go to `<out>.children.csv` (beside `<out>.csv`): `parent_link` (the row's link cell), `parent_row` (the row's 1-based number among the main CSV's data rows), `child_index` (1-based place among that page's kept child rows, after `require`), then the child columns. Join on `parent_row`; a link in several rows is read once and its children are listed under each of those rows, so each row's `children_count` equals its child rows. Child column names may not be `parent_link`, `parent_row` or `child_index`. A run without `children` to the same `--out` moves an old `<out>.children.csv` to `<out>.children.stale.csv` (the summary says so): don't report it as current.
- The summary's `children` part: `rows` (rows in the child CSV), `okPages`, `pagesWithNone` (ok pages without children: open one and check it shows none), `fillRate` per child column over the child rows, `capped` (pages where `max` cut the list), `childErrors` (pages whose children could not be read). Each warning names a page to look at; fix what it points to and rerun (a changed config reads every page again):
  - children could not be read: CSS the page rejects in `children.rows` or a child field (the page's own fields still read).
  - `children.rows` matched nothing on any ok page; a child column filled far less than the others; child rows that read nothing in any column (`rows` matches more than the rows).
  - child rows from several separate places on the page (no `root`, or `rows` too wide); a container matched together with its rows.
  - a control beside the child rows that is not in `expand` ("View all 32 answers"), or a count beside them ("Comments (32)") larger than the rows read.
  - an `expand` control still there after the last round: raise `expandPasses`, or report that those items have more children than were read.
  - matches the page does not show, on pages without children (rows in a closed tab: open it in `setup`); a link beside the child rows to more of them on another URL (next).
- **A child list that pages through other URLs** (its page 2 is a URL of its own, or "See all 120 reviews" opens a separate reviews page): detail.mjs reads only the children the item's page itself shows, and warns when it sees such a link. To get the rest, collect it separately. When the whole list is on one page of its own ("See all reviews" shows them all, maybe behind a load-more button), read that link as a detail field (`attr: "href"`) and run a second detail pass over the output with `link` set to that column and `children` (plus `expand`) reading that page; its child CSV joins on `parent_row` like the first and replaces the first pass's child rows for those items: that page usually repeats the ones the item's page showed, so do not concatenate the two. When the list goes on page by page through URLs, run collect.mjs on each item's list URL (its `next` follows the pager), one run per item, and join on the item's link. Say in the report which items have more children than were read.

## Things to report

The summary's `status` counts (per row, the same as the `detail_status` column: ok / empty / failed / blocked / pending / no-link; `deadLinks` among the empty ones), the fill rate of each detail column, and how the run ended. Rows whose page failed or was blocked keep their list data with empty detail cells; say how many, and that rerunning the same command fills them in. With `children`: the child CSV's path and row count, the ok pages without children, each child column's fill rate, and items whose list continues elsewhere, was cut by `max` or by `expandPasses`.
