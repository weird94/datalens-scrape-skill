# 经典站点 pattern 汇总 + 本地演练场方案（2026-10-19）

来源：8 月底到 10-19 的排查与实验——分页外链误杀、死分页控件、频道 tab 当分页器、零候选、
10-11 准确度清单、10-12/10-13 真站走查（227 站）、round 2/2b/2c/3a/3b、10-18 全量零 AI 重跑（125 站）、
10-19 AI 停机决策评测。每条 pattern 都标了出处，方便回查原始证据。

## 0. 结论

- 这两个月踩到的问题，绝大多数可以归进 **24 个 pattern**（§1）。它们不依赖具体站点，在任何技术栈上都能用几十行 HTML/JS 复现。
- 现有离线资产（134 页存档语料、19 个 jsdom 夹具、34 个停机现场）都是**静态快照**：能测检测和列识别，**测不了执行循环**（滚动、翻页、续载、整页跳转、晚渲染）。而 10-18 的重跑里，没采满的站点一半问题出在循环和翻页配置上。本地演练场要补的就是这块：**会动的 mock 站点**。
- mock 站点的另一个好处是**有标准答案**：总行数、末页、该停的原因都由我们定，判卷是精确的；真站只能靠截图和「页面自称总数」猜，而自称总数常常和能采到的行数对不上（腾讯评论 160 对 123、澎湃 361 对 49）。
- 建议的分工：**日常改动只跑本地**（mock + 存档语料）；**改了检测/选列启发式时加跑存档语料**；**只在发版前或重大改动时跑一小组真站**（10 站左右，每站一次），全量 227 站只在里程碑跑。§4 有具体规则。
- mock 解决不了的：真实反爬、登录态、站点改版、模型在真实杂乱 DOM 上的随机性。所以真站不会完全取消，只是从「每次都跑」降到「关键节点抽查」。

## 1. Pattern 目录

按采集管线的阶段分组。「状态」一栏：已修 / 部分修 / 未修 / 设计内（不是 bug，但 mock 要覆盖以防回退）。

### A. 页面就绪与检测

| # | Pattern | 典型站点 | 机制 | 状态 | mock 要模拟什么 |
|---|---|---|---|---|---|
| A1 | **列表晚渲染** | 任何 CSR 站、Trustpilot（WAF 质询后才渲染） | 检测一发定生死，列表 1.5s 后才插入 → 结构树为空、零候选，连 AI 都不调 | 修复声称：`918eb2e9` 就绪等待（load + DOM 安静 400ms，上限 4s）；**未经演练场 oracle 或扩展实跑验证**，mock 的 A01 case 不得据此标绿 | 列表延迟 N ms 插入；N 可调（1500 / 3000 / 5000，最后一档超过上限，验证降级行为） |
| A2 | **虚拟列表检测时只渲染了一条** | 微博帖子评论（`vue-recycle-scroller`） | 检测那一刻只有 1 条主评论，树里只剩它下面的回复子列表 | 未修 | 虚拟滚动列表，首屏只挂 1–2 条，滚动后回收旧节点 |
| A3 | **递归嵌套包装** | Spotify discography | 每层 = 1 项 + 一个装剩余项的 wrapper，树被切成多层每层 2 项 | 未修 | 递归 wrapper 结构的列表 |
| A4 | **表格行 class 不一致 + 插入分组行** | 企查查搜索 | `tr` 的 class 有 `frtrt` / 空 / `blur`，中间插「其他相关结果」行，相似度判定失败 | 未修 | 表格里混 3 种 class 的数据行 + 2 条分隔行 |
| A5 | **瘦页 / 中间页 / 软 404** | YouTube 登出首页、Shopee 语言选择页、雪球「内容已删除」、拼多多「暂无评价」 | 页面本身没有列表，应报 PAGE_EMPTY / GATED / 死链，而不是零候选 | 部分修（判卷侧有规则，产品侧文案提示不全） | 几种 <200 字的空页、中间页、软 404 文案 |
| A6 | **内容在 Web Component 的 shadow root 里** | Reddit 帖子（作者 / 赞数是属性，正文在 light DOM，帖子头「1.5K」评论数和投票数只在 `shreddit-post` 的 shadow root 里）；Lit 一类组件库站点（字段整个画在组件自己的 shadow root 里） | `querySelectorAll` 和 `innerText` 都停在 shadow 边界：行（自定义元素本身）看得见，shadow 里的字段读出空列，页面自称的总数、到底文案、shadow 里的加载更多按钮全看不见；skill 把「找不到按钮」当成到底，报 `load-more-gone` 收工（10/30 行） | skill 已修（2026-11-10，`in-page.mjs` 查询和读文字都进 open shadow root；2026-11-11 起后代选择器（空格）可跨 shadow 边界，`>` 不跨；closed shadow root 仍读不到），case A06-001、A06-002（多层嵌套、主评论与回复同 id、回复折叠 + 行内分页、滚动加载）；产品检测链路未测 | 评论卡片是自定义元素，作者 / 时间 / 赞数在卡片 shadow root、正文经 slot 投入；页头总数和加载更多按钮各在组件 shadow root；首批声明式 shadow DOM、后续 attachShadow |

| # | Pattern | 典型站点 | 机制 | 状态 | mock 要模拟什么 |
|---|---|---|---|---|---|

## 3. 本地演练场方案

### 3.1 放在哪

沿用 `dev-fixtures` 的做法：**由 backend dev server（:3008）吐页面**。原因已在那个路由的注释里写了：扩展的 content script 只匹配 `https://*/*` 和 `http://localhost:3008/*`，另起静态服务采不到。生产环境返回 404 的守卫保留。

建议目录：`packages/backend/src/app/dev-fixtures/playground/<pattern-id>/...`，每个 pattern 一个路由，行为用 query 参数调，例如：

```
/dev-fixtures/playground/late-render?delay=1500&rows=20
/dev-fixtures/playground/numbered-pager/1?pages=12&perPage=10&arrowOnly=1
/dev-fixtures/playground/infinite-io?batches=8&batchSize=30&innerScroll=1
/dev-fixtures/playground/captcha-after?page=1&wallAt=4
```

### 3.2 每个 mock 必须带标准答案

每个 mock 同时暴露一份清单（如 `/dev-fixtures/playground/manifest.json`），每个用例写明：

- `expectedRows`：能采到的总行数（不是页面自称数，E3 专门测两者不一致）
- `expectedStop`：`end-of-list` / `wall` / `blocked` / `page-empty` / `dead-link` / `gated` / `stuck` / `budget`
- `expectedColumns`：关键列的名字和前 3 行的值
- `patterns`：对应 §1 的编号

判卷因此可以精确比对，而不用靠截图和猜。

### 3.3 跑法

复用真站走查的 runner，不另写：给 `test/sites/` 加一份 `local-sites.json`（或在 `sites.json` 里加 `env: local`），`pnpm e2e:walkthrough --registry local`。judge 增加一条「对照 manifest 精确判卷」，有清单时优先用它。

### 3.4 防止对 mock 过拟合

mock 也是一种夹具，和 10-19 的提醒同一个风险：提示词和启发式容易调成只对 mock 有效。

- **mock 不用真站名字和真站 class**。类名、文案、语言随机化（同一 pattern 至少中 / 英 / 日 三种文案；class 用随机 hash 或语义名两种变体）。
- **每个 pattern 至少 2 个变体**，其中 1 个作为留出集，平时不看、只在验收时跑。
- **mock 通过不等于修好**。修复的验收仍然是：mock + 存档语料 + 发版前真站抽查 三者都不退化。
- 继续执行「流程收尾派 subagent 审提示词是否过拟合」，审查时把 mock 的文案也列进「评测里出现过的站点清单」。

### 3.5 第一批（建议按这个顺序）

按「10-18 重跑里丢数据最多、且现在只有真站能测」排序：

| 批次 | mock | 覆盖 pattern | 估计工作量 |
|---|---|---|---|
| 1 | 数字页码分页器（含只有图标的箭头、末页不置灰） | D7, D12, E1 | 小 |
| 1 | 整页跳转分页（新页容器晚渲染 / class 变化） | D5 | 小 |
| 1 | IntersectionObserver 无限滚动（内部滚动容器变体） | D8, D9, E2 | 中 |
| 1 | 干扰控件大杂烩（轮播箭头、展开、筛选链接、spinner、频道切换组、侧栏换一换 + 真加载更多） | D3, D4, D6 | 中 |
| 2 | 晚渲染 / 质询后渲染 | A1, F1 | 小 |
| 2 | 第 N 页后验证码 / 限流挂起 | F4, F5, E4 | 小 |
| 2 | 弹窗锁滚动 | D11 | 小 |
| 2 | 翻页后分两批插入 | D10 | 小 |
| 2 | 自称总数 ≠ 可采数 | E3 | 小 |
| 3 | 列提取组合页（斑马纹、rowspan、多一层 wrapper、hash class、aria-label 数值、懒加载图） | C1–C9 | 中（很多已有 jsdom 夹具，可以直接搬进来变成真页面） |
| 3 | 检测难例（虚拟列表、递归嵌套、混 class 表格、详情页小列表、异构模块、瘦页） | A2–A5, B1–B5 | 中 |
| 3 | 登录墙三种形态、403 页 | F2, F3 | 小 |

第 1 批 4 个 mock 就覆盖了 10-18 重跑里「循环问题 + 配置问题」11 站中的 9 站对应的形状。

### 3.6 把它做成持续长大的 case 库（AI infra）

目标：演练场不是一次性的一批 mock，而是**一个持续积累的 case 库**。以后遇到任何新问题都沉淀进来；AI 在开发循环里既能拿它跑测试，也能直接读它，作为「我们见过哪些网页形状、哪些已解决、哪些还没解决」的记忆，用来推理下一步往哪个方向改。线上页面会变，**pattern 不会变**，所以库的基本单位是 pattern，不是站点。

**两层结构**

```
test/playground/
  patterns/
    D07-missing-numbered-pager.md     ← pattern 卡片：机制、为什么难、当前状态、相关代码、修过什么、没修什么
  cases/
    D07-001/                          ← 一个 case = pattern 的一个具体形状
      case.json                       ← 元数据（见下）
      page/                           ← mock 页面（由 dev-fixtures 路由读取渲染，或静态 HTML + 行为脚本）
      expected.json                   ← 标准答案：expectedRows / expectedStop / rowMatch / oracle / naive（错误做法的行数）/ stopSignal / trapVerifiedBy
                                       （schema v2 的完整字段说明见 packages/e2e-harness/src/playground-oracle.ts 文件头）
      evidence/                       ← 来源证据：真站截图、存档 DOM 片段、日志节选（只放小文件）
  INDEX.md                            ← 自动生成：pattern × case × 最近一次结果的总表，给 AI 和人读
  results/<date>/                     ← 每次跑的结果（gitignored），INDEX 从最新一次汇总
```

`case.json` 至少包含：`pattern`（§1 编号）、`source`（来自哪个真站、哪天、哪次 run，或「合成」）、`variant`（语言 / class 风格 / 时序参数）、`heldOut`（是否留出集）、`status`（red = 当前失败 / green = 通过 / known-gap = 已知不修）、`relatedCode`、`relatedDocs`。

**新 case 的入库流程**（每次遇到新问题都走这一遍，以后固化成一个 skill）：

1. 真站或用户报的问题，按现有证据规则查到第一个出错的边界。
2. 对照 `patterns/`：属于已有 pattern → 加一个新 case（新形状 / 新变体）；都不像 → 新建 pattern 卡片。
3. 用通用的类名和文案写 mock，**不抄真站名字和 class**；从真站只带走「形状」和证据。
4. 写 `expected.json`，先跑一遍确认是 **red**（复现了问题），才算入库成功。
5. 修复后同一个 case 变 green；pattern 卡片更新「修过什么、还剩什么」。
6. 之后回归只跑这个 case，不再访问那个真站。

**AI 怎么用它**

- **当测试集**：改执行循环、提示词、启发式时，跑全库，看 red → green、green → red 的变化。
- **当记忆**：动手前先读 `INDEX.md` 和相关 pattern 卡片，知道这个形状以前怎么坏、怎么修、哪个方案被否过（比如 3a A5 per-cell aria-label 在留出语料上变差），避免重复踩坑。
- **当路线图依据**：按 pattern 统计 red 数量、在真站走查里出现的频率、丢的行数，直接排出「下一个最值得修的形状」；也能看出哪一类问题规则已经兜不住、需要交给 AI 判断（和 AI 停机决策这条主线对得上）。
- 记忆目录里只留一条指针指向 `test/playground/INDEX.md`，细节都在库里，不在记忆里重复。

**和现有资产的关系**：19 个 jsdom 夹具、34 个停机现场、冻结测试、存档语料里能对应上 pattern 的，第一步就按 pattern 编号登记成 case（不必重写，`case.json` 指向原文件即可），库一开始就有几十个 case，不是从零开始。

## 4. 真站什么时候用

| 场景 | 本地 mock | 存档语料 | 真站 |
|---|---|---|---|
| 日常改动、调提示词 | 必跑 | 改检测 / 选列时跑 | **不跑** |
| 修某个真站报的 bug | 先把它做成 mock，在 mock 上复现 → 修 → 验证 | 跑 | 修完后**只访问那一个站一次**确认 |
| 合 PR 前 | 全量 | 全量 | 不跑（除非 PR 就是为真站修的） |
| 发版前 | 全量 | 全量 | P0 小组 10 站左右，每站一次 |
| 里程碑 / 月度 | 全量 | 全量 | 全量 227 站一次，顺便把新问题沉淀成 mock 和语料 |

控制访问频率的硬规则：

- 同一个真站**每天最多访问 1 次**（walkthrough runner 加一个按 host 的冷却记录，跨 run 生效）。
- 已知 headless 必拦的站（Etsy、eBay 搜索、Tripadvisor 等，见 `real-site-walkthrough` 记录）**不进常规真站集**，它们的 BLOCKED 判定用 F2 mock 测。
- 真站跑出的每个新问题，**先存档页面进语料，能做成 mock 的做成 mock**，之后就不需要再访问这个站来回归。这是真站访问量能持续下降的关键。

## 5. mock 测不了的（真站仍然必要的理由）

- 真实的反爬策略和它的变化（今天能开、明天 403）。
- 登录态下的页面（owner 认为要求用户登录可以接受，这部分只能在真浏览器里测）。
- 站点改版：mock 是冻结的，真站会变；存档语料能部分弥补。
- 模型在真实、杂乱、超大 DOM 上的选择随机性（如 Gartner 那次 AI 选了 3 项列表）。mock 的 DOM 太干净，会高估模型准确率。
