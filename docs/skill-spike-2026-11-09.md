# Skill 可行性验证：采集引擎能否脱离插件运行（2026-11-09）

## 要回答的问题

如果把 DataLens 做成一个 skill，现有的采集引擎（core 识别 + 翻页/滚动/停机循环）能不能直接拿出来用？还是得在插件外面重写？

这次验证不回答：agent 能不能选对列表、给字段起好名字；真实网站上的效果；要登录的站；有没有人想用。

## 做法

不改任何产品代码，用 Playwright 代替 Chrome 扩展来驱动产品的两半执行层：

```
Node 进程
  ExecutionControllerImpl   产品后台的采集控制器，原样
     │ executionService.fetchData() / clickNextPageButton() …
     ▼
  rpc-shim.ts               替换 crx-rpc 的 createClient：方法调用 → page.evaluate
     ▼
无头 Chromium
  page.js（addInitScript，每次整页跳转后自动重新注入）
     ├─ @general-scraping/core          列表识别，原样
     └─ ExecutionServiceImpl            content script 执行层，原样
        ▲
演练场页面 ← serve-fixtures.mts（直接调 dev-fixtures 的 route.ts，不用起 Next）
```

- 适配代码约 200 行：`rpc-shim.ts` 61 行、`node-entry.ts` 103 行（含 `IChromeTab` 的 Playwright 实现）、`page-entry.ts` 39 行。
- 三个 AI 注入点全部置空：`IStopAdvisor`、`IListRelocator`、页面侧的 `detectNextPage`。不调任何模型，没有外网请求（已核对打包产物和进程的网络连接）。
- agent 要做的两件事用标准答案代替：从候选里挑哪个列表（按 `expected.json` 的 rowMatch），以及「点下一页 / 加载更多」的按钮选择器（按 oracle 的 clickSelector）。字段取行内全部叶子节点，经 core 的 `postProcessSchema` 生成。
- 脚本和原始结果在 `.codex-tmp/skill-spike/`（已 gitignore）。`run-all.sh` 里写死了当时会话 scratchpad 的路径，复跑前要改。

## 结果

### 识别（57 个 case）

| | 数量 | 结果 |
|---|---:|---|
| 有数据的 case | 51 | 50 个识别出了正确的列表（候选第一位） |
| 空页面（瘦页、软 404、登录门、拦截页、403） | 6 | 6 个都正确给出 0 候选 |

- A01-002/003（晚渲染 2.5–3 秒）第一次识别是 0 候选，等 2 秒重试后命中。skill 里要写明「0 候选就等一下再识别」，这就是之前查到的零候选根因。
- B01-001 漏了：页面上有 3 条评价和 20 张推荐卡片，core 只给出推荐轮播。3 行的小列表进不了候选。
- 识别耗时中位数 9ms，最长 51ms。

### 完整采集（有数据的 51 个，不调 AI）

**41/51 一次通过**，包括虚拟列表 200 行、两种无限滚动各 240 行、12 页整页跳转、验证码墙前停下、续载挂起、标称总数虚报。

失败的 10 个都和「脱离插件」本身无关，分成三类：

| 类别 | case | 情况 | agent 版本复验 |
|---|---|---|---|
| 自动生成的选择器跨页不稳定 | D05-001、D05-003、D05-004 | 第 2 页起容器的 class 或包装层变了，只采到第 1 页 10 行。产品里由 AI 重新定位兜底，这次置空了 | 手写稳定选择器（`ul[class^="result-list-p"]`、`div:has(> div.item)`），不调 AI，3 个全部采全：60/60、30/30、30/30 |
| 选列表的粒度 | C05-001 | 有两个候选：按组合并的（5 行）和平铺的（20 行），验证脚本选了前者 | 选平铺的那个：20/20 |
| 混进了非数据行 | A04-001（+2 行分组标题）、C08-001~003（+1 行「查看全部」控件） | 数据行一行不少，多出的是非数据行 | 没复验；skill 的质检步骤要能发现「这一行和其他行字段形状不一样」 |
| 识别漏掉 | B01-001 | 3 行的小列表不在候选里 | 没复验；引擎接受任意选择器，agent 可以自己写 |
| 采集中途弹窗锁滚动 | D11-001 | 采到 20/40；规则版的关弹窗没生效 | 没复验；产品里由 AI 停机顾问补救，skill 里交给 agent |

算上复验的 4 个，**由 agent 来做选择时 45/51**。剩下 6 个里，4 个需要质检过滤非数据行，1 个需要 agent 自己写选择器，1 个需要采集中途的补救。

### 耗时

通过的 case 中位数 61 秒，最长 86 秒。单页列表也要约 60 秒才收尾：没有 AI 停机顾问时，控制器只能靠「连续很多轮没有新行」判定结束。

## 结论

1. **引擎可以原样搬出插件**。产品代码已经把浏览器能力抽象成了接口（`IChromeTab`、crx-rpc、三个可选的 AI 注入点），换宿主只需要约 200 行适配代码。
2. **自动生成的选择器是失败的主要来源之一，agent 手写的稳定选择器能顶替 AI 重新定位。** 这支持「skill 里让 AI 直接读页面拼选择器」的方向：插件为了省钱做的「清洗后交给 AI」那一层，在强模型加验证的回路里可以拿掉。
3. **skill 的核心资产是验证器**：剩下的失败大多是「哪些行算数据」，要靠质检发现，比如行的字段形状不一致、行数与页面可见条目对不上。core 的 `quality` 模块可以作为起点。
4. **停机要交还给 agent，或者让 skill 自己调模型**。否则单页列表也要等一分钟。
5. 同一套适配接口可以服务三种组合：独立 skill（Playwright）、插件内置 agent、用户自带 agent 加插件当运行时（MCP bridge）。

## 下一步建议

做一个最小的薄 skill 原型，包含 `inspect` / `collect` / `verify` 三个脚本、SKILL.md 和 references。用这次搭的演练场服务器加运行脚本改成评测台，跑同一批 case，和本次的引擎基线（41/51 自动、45/51 agent 选择）对比。
